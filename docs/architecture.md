# 架构与实现

本文解释 iptables-web 如何把页面操作转换为可核验、可恢复的防火墙变更。安装参数见[部署与配置](deployment.md)，日常操作和故障处理见[运维手册](operations.md)。

## 组件

项目构建两个 Go 二进制：中心端 `iptables-web` 和目标机 `iptables-web-agent`。只有中心端嵌入原生 HTML、CSS、JavaScript 前端；Agent 复用规则存储、iptables 执行器、审计和回滚逻辑，但只暴露固定 API。

```text
Browser
  └─ Controller Web UI / HTTP API
       ├─ 认证与角色校验
       ├─ Agent 签名申请、待确认队列与回连验证
       ├─ 主机清单与 host_ids / host_groups 授权
       ├─ 固定允许列表代理 ──► Agent API
       ├─ 规则模型与顺序校验
       ├─ JSON 数据存储
       ├─ 变更审计与回滚
       ├─ packet executor
       │    └─ iptables / iptables-nft
       ├─ Docker 映射发现
       │    ├─ Docker socket
       │    └─ docker CLI
       └─ 规则助手（只生成或解读文本）
```

启用多主机后，当前实例承担控制端角色。Agent 首次启动生成 Ed25519 身份并主动提交签名申请，管理员批准时控制端回连其受保护状态接口；成功后凭据经 AES-GCM 保存。批准 Agent 的后续签名申请同时作为心跳，控制端记录最近上报时间，界面默认以 45 秒为离线阈值，可由全局或逐主机设置覆盖，并把“Agent 未上报”和“Agent 在上报但中心回连失败”分开表达。浏览器仍只连接控制端；控制端根据打开的主机，把允许列表中的规则、系统和 Docker 请求通过 HTTP 或 HTTPS 及独立凭据转发到目标 Agent。控制端本机使用保留主机 ID `local`，计入纳管总数和在线数；管理员始终可管理，普通用户只有被逐台授予 `local` 后才能通过概览或侧栏调用本机固定 API。目标机继续使用自己的执行器、数据文件、审计和回滚，不共享内存状态。

审批会在选择申请时清理过期项，并在网络验证结束后重新确认申请未过期、未被拒绝且待审批配置未改变。同地址凭据轮换和已审批地址迁移只更新连接配置及加密凭据，保留管理员在验证期间修改的名称、分组和启停状态；已验证端点、CA 或凭据若同期变化则要求重试。心跳时间只前进，较早完成的请求不会覆盖更新的上报时间。

部署时不需要 Node.js、数据库或独立 Web 服务器。进程需要足够权限操作宿主机 packet 防火墙。

## 一次规则变更如何执行

以“允许 `10.10.0.0/16` 访问 Docker 发布端口 `10089`”为例：

1. 页面收集链、来源、端口和动作，并先显示字段级预览。
2. 管理员确认后，浏览器向 Go API 提交结构化 JSON。
3. 认证中间件验证会话、首次改密状态和角色权限。
4. 服务端校验地址、端口、链、动作、规则范围和白名单顺序。
5. 写操作取得进程内互斥锁，并保存变更前托管规则快照。
6. 服务端更新声明状态，将规则转换为独立的命令参数。
7. 执行层等待 xtables 锁，在超时限制内同步对应链。
8. 服务端重新读取运行态规则进行核验。
9. 成功后写入审计并开启回滚窗口；失败时恢复变更前状态。

外部命令不使用请求内容拼接 shell 字符串。规则字段在模型层标准化后作为独立参数传给执行器。

## 声明状态与运行状态

程序同时处理两种状态：

- `rules.json` 是声明状态，表示页面希望系统维持的托管规则；
- Linux 内核中的 iptables 是运行状态，实际决定数据包是否放行。

新增、编辑、启停、删除和排序都会以同一链的声明状态重新同步运行状态。服务启动时也会恢复已启用规则，因此主机或服务重启后不需要人工重建。

删除不存在的运行态规则视为成功，使启停和清理保持幂等。程序不会 flush 系统链；同步、回滚、清空和卸载时只删除带有 `iptables-web:<rule-id>` 所有权标记且条件对应的规则，再按有效位置加入当前启用规则。不会把条件相同的无标记规则当成自己的规则，也不在启动时自动删除旧版无标记规则；历史残留需要管理员备份后人工核对。

`FIREWALL_BACKEND=auto` 使用系统默认 `iptables`；显式选择 `iptables-nft` 或 `iptables-legacy` 时，执行器使用对应的 IPv4 命令、save/restore 及 IPv6 备份/恢复命令家族，工具缺失时拒绝悄悄回退。

托管模型当前只有 `packet` 后端，支持 `INPUT`、`FORWARD`、`OUTPUT`、`DOCKER` 和 `DOCKER_USER`，以及 `ACCEPT`、`DROP`、`REJECT`、`LOG`、`RETURN` 动作。IPv6 托管规则会被拒绝，Docker IPv6 映射目前只读。

## 数据文件

默认情况下，数据文件与 `RULES_FILE` 位于同一目录：

| 文件 | 内容 | 写入方式 |
| --- | --- | --- |
| `rules.json` | 托管规则及顺序 | 临时文件写入后原子替换 |
| `users.json` | 用户、当前/历史密码哈希、角色、改密时间、禁用/强制改密状态、逐台与主机组授权 | 临时文件写入后原子替换 |
| `security-policy.json` | 密码复杂度/有效期、历史/差异规则、验证码策略、锁定策略和重置默认密码哈希 | 临时文件写入后原子替换 |
| `hosts.json` | 远程主机清单、最近心跳、AES-GCM 加密后的 API Key、可选 CA | 临时文件写入后原子替换；心跳最多每台每分钟落盘一次 |
| `monitoring-policy.json` | 全局在线检测默认值 | 0600；管理员动态更新 |
| `hosts.key` | 自动生成的远程凭据 AES-GCM 主密钥 | 首次启动原子创建；与 `hosts.json` 成对备份 |
| `api-keys.json` | 动态访问密钥元数据及 SHA-256 哈希，不含明文 | 临时文件写入后原子替换 |
| `audit.jsonl` | 追加式受认证变更记录，包含操作者和脱敏差异 | 逐条追加 |
| `rollback.json` | 最近一次规则变更前快照 | 临时文件写入后原子替换 |

Agent 另有权限为 `0600` 的 `agent.identity` 和 `agent.key.sha256`。私钥只用于签署纳管申请，管理凭据明文不落 Agent 磁盘。中心待确认队列只在内存中保存，重启后由 Agent 周期重报。

安装器创建的数据目录权限为 `0700`，数据文件权限为 `0600`。登录会话、验证码和定时锁定计数只保存在进程内存中，服务重启后失效；管理员解锁模式产生的账户禁用状态会持久化。验证码使用加密随机数生成，每次都包含大写字母、小写字母和数字；新安装默认不区分大小写，之后由持久化安全策略控制，已生成的验证码保持生成时的校验方式。新安装的密码策略默认只要求非空且不超过 128 字符，复杂度、历史和差异要求由管理员登录后配置；已有持久化策略升级时保持不变。

持久化失败时，服务端会恢复内存中的旧值；内核同步失败时，会恢复声明状态并尝试重新同步旧规则。这个机制只覆盖本程序托管内容，无法恢复外部规则、路由或网络命名空间。

## Docker 流量路径

宿主机服务和 Docker 发布端口经过不同路径：

```text
宿主机服务
客户端 ──► 宿主机端口 ──► INPUT ──► 宿主机进程

Docker 发布端口
客户端 ──► 宿主机:10089 ──► DNAT ──► 容器:8080
                              │
                              └──► FORWARD ──► DOCKER-USER
```

外部请求到达 `DOCKER-USER` 时，普通 `dport` 可能已经变为容器端口。`original_dport` 使用 conntrack 的原始连接元组匹配 DNAT 前宿主机端口；`original_dest` 可进一步区分宿主机地址。

托管模型不允许同时设置 `dport` 与 `original_dport`。iptables 表达式在 `--ctorigdstport` 后增加 `--ctdir ORIGINAL`，只匹配客户端到容器的原始方向，避免兜底 DROP 拦截返回包。

Docker 映射只来自只读 Docker socket 或 Docker CLI。普通监听端口不能证明由 Docker 发布，因此不会被当作映射。创建 Docker 策略前，服务端还会检查 `DOCKER-USER` 链以及 `FORWARD → DOCKER-USER` 跳转是否真实可用。

## 在线检测与主机搜索

中心使用独立的 MonitoringStore 持久化 `monitoring-policy.json`，默认回连间隔 60 秒、心跳离线阈值 45 秒。ManagedHost 的同名字段为 0 时继承全局，非 0 时覆盖；更新 Agent 端点或轮换凭据保留这些管理员设置。Agent 上报与 UI 刷新仍固定为 15 秒。

回连检测只访问受保护的固定状态接口，中心按主机缓存成功或失败结果，并合并并发请求。缓存包含端点、CA、加密凭据指纹，避免配置变化后复用旧结果。自动检测由打开的页面触发，手动检测可跳过缓存，不提供后台全时探测。设置只属于中心，不进入 Agent 或任意 URL 代理。

纳管搜索仅过滤服务器已授权返回的清单，按名称、地址、分组和 Agent ID 做不区分大小写的包含匹配，多个关键词同时匹配；不会扩大主机可见范围。

## Docker 批量变更

界面按容器身份聚合发布端口，再显示每个端口的托管来源、兜底和禁用规则。清空从明确归属的规则 ID 建立已确认列表；不按容器名称描述推断未知规则，不直接 flush Docker 链。

批量新增在脱离持久化的临时规则存储中规划全部来源和端口，完成去重、补齐兜底和全链顺序校验后再应用。批量删除先验证全部 ID 和可选更新时间，任一冲突不执行前缀。两类操作在同一个主机变更锁内写盘、同步并核验，失败时补偿恢复；审计及最近回滚覆盖整个批次。链位置未改变的规则在规范化时不刷新更新时间，避免把无关记录误报为修改。

## 身份认证

登录成功后，服务端创建内存会话，浏览器在当前标签页的 `sessionStorage` 中保存 Token，并通过 Bearer Token 调用 API。

默认管理员、管理员新建用户、被重置密码的用户以及密码过期用户带有或动态进入 `must_change_password` 状态。认证中间件在服务端只允许这些会话访问会话检查、修改本人密码和退出接口，不能通过绕过前端页面调用其他 API。改密成功后状态清除并刷新改密时间，该用户全部旧会话同时撤销。

密码策略在服务端强制执行。复杂度调整只影响后续创建、重置和修改密码；有效期在登录和会话校验时动态计算。密码历史和账户重置默认密码只保存 PBKDF2 哈希，不保存明文或可逆摘要；安全策略 GET 只返回默认密码是否已配置。字符差异规则只在用户提交当前密码时逐字符比较；管理员重置会应用预设默认密码哈希、清除锁定、撤销会话并强制用户再次改密。

连续失败次数按账户累计，避免通过更换来源 IP 绕过。定时模式在内存中锁定配置的分钟数；管理员模式把禁用状态写入用户记录，管理员可独立解锁而不修改密码。为保留恢复路径，最后一个未持久禁用的管理员不能被降级或删除，登录失败时也只进入定时锁定；这些判断在用户存储写锁内完成，避免并发操作使管理员数量变成零。验证码在一个写锁内完成校验和消费，同一挑战不能被并发复用。无论 UI 是否隐藏，规则、本机系统和 Docker API 都通过服务端 `local` 授权中间件校验；中心本机审计因包含用户、主机和密钥管理信息而额外要求管理员权限。

角色、逐台主机和主机组授权在每次会话校验时从当前用户记录刷新。主机组按名称动态解析，组内已有主机和以后加入该组的远程主机都继承授权；内置 `local` 不参加分组授权。用户删除、账户重置或本人改密会撤销相关会话。

## 审计、备份与恢复

规则、Docker 白名单、用户、密码、安全策略、Agent 审批/拒绝、主机与中心访问密钥管理、完整恢复和清理操作由审计中间件捕获。记录包含请求 ID、操作者、角色、来源地址、方法、路径、动作、HTTP 结果和可用的脱敏前后差异，不记录密码、密码历史、Token、Agent Key、中心 API Key 或 CA 内容。远程请求由中心用每主机 Agent Key 认证，并附带中心已认证的操作者、角色、原始来源 IP 与请求 ID；Agent 只有在 Key 验证成功后才信任这些字段，浏览器会话 Token 始终留在中心。

每次成功改变托管规则后，变更前快照保留 10 分钟。回滚会精确删除当前托管规则、恢复快照、重新同步并核验；回滚前状态随后成为新的反向回滚点。

完整备份与本程序的规则变更共用互斥锁，避免在写盘与内核同步之间导出不一致的托管元数据；程序外的规则修改仍需在维护窗口协调。规则、用户和回滚数据会检查空记录、重复标识及相应字段，损坏数据不会继续进入规则执行。旧版 firewalld 元数据清理和 Docker 端口字段迁移仍由既有启动流程处理。

系统页的完整备份是带版本清单的组合 JSON，包含：

- IPv4 `iptables-save` 结果；
- 可用时的 IPv6 规则集；
- `managed-rules.json` 托管记录；
- 描述文件名和格式版本的 manifest。

完整恢复会先检查清单和规则语法，再备份当前状态并以替换语义应用；失败时尝试恢复旧规则。命令和应急步骤见[运维手册](operations.md)。

## 管理边界

- Web 管理只写入 iptables 或 iptables-nft 兼容后端；
- 原生 nftables 写入后端已禁用；
- firewalld Zone 和 rich rule 由程序外部管理；
- 规则助手可生成 ip6tables、nftables 和 firewalld 文本，但不会执行；
- 卸载和清理只处理托管规则，不 reload firewalld，不 flush 未知链。
- 中心和 Agent 的常规同步、清空、回滚及卸载均不执行无所有权注释的兼容删除。

这些边界用于避免多个防火墙管理面相互覆盖。对外暴露、运行权限和高风险操作要求见[部署与配置](deployment.md)和[运维手册](operations.md)。

## 主机资料并发编辑

管理员保存资料时，存储层核对读取时的地址、CA、身份与凭据版本；若已被签名审批或凭据轮换改变，拒绝旧资料覆盖，要求刷新后重试。心跳保留最新已验证时间，不因资料编辑回退。Agent 更新连接时同样保留最新管理员名称、分组、启停与检测设置。
